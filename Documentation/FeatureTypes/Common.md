# Common steps for every feature

> Applies to every feature, whatever it does. Skill features have their own process in [`../SkillTypes/Common.md`](../SkillTypes/Common.md) (SID enum, skill text, SkillInfo). Paths are relative to the repo root. Line numbers were checked against the tree when this file was written.

## Anatomy

A feature is a folder under `Kernel/Wizardry/<Feature>/`. Three recent features show the pattern:

| Commit | Feature | What it added |
|---|---|---|
| `0e82892cf` | PopupIconShine | Installer with include guard, one `LynJump.event` entry, one `.c`, a designer toggle, a doc, a README bullet and a GIF |
| `4367e1604` | LanguageSelect | Installer without a guard, `Gfx/` (png and the `.lz77` made from it), a pointer patch in the installer, a RAM slot, a header in `include/kernel/` |
| `3f9a1e53a` | ClassGrowths | Installer with guard, two `.c` files, `LynJump.event` with three entries, edits to existing feature files, a header change, a RAM slot, a toggle, a doc (no GIF) |

Study any of them with `git show --stat <hash>`.

The fullest folder is ClassGrowths:

```
Kernel/Wizardry/ClassGrowths/
├── ClassGrowths_Installer.event       include guard; includes the files below
└── Source/
    ├── ClassGrowths.c                 code
    ├── ClassGrowths.lyn.event         generated by make from the .c; committed
    ├── ClassGrowthPreview.c           second code file, same pattern
    ├── ClassGrowthPreview.lyn.event
    └── LynJump.event                  vanilla functions this feature replaces
```

What each piece is for:

- `<Feature>_Installer.event`: the only file `Kernel/Wizardry/wizardry.event` includes. Everything else is included from here.
- `Source/<Feature>.c`: the code.
- `Source/<Feature>.lyn.event`: generated from the `.c`, see [Installer and lyn](#installer-and-lyn).
- `Source/LynJump.event`: only when a vanilla function is rewritten.
- `Gfx/`: only for graphics. LanguageSelect keeps `Img_LanguageSelectFlags.png` and the `.lz77` made from it, both tracked in git.
- `data.event`: only for a hook list that the kernel walks, such as `Kernel/Wizardry/PostActionHook/data.event`. It is wired in the `WIZARDRY_DATA` block, see [Where the code goes](#where-the-code-goes-kernel-vs-wizardry_custom).

Installers can also patch vanilla data directly, without a LynJump. LanguageSelect does this for its boot screen:

```
PUSH
    ORG 0x591710
    POIN ProcScr_LanguageSelect
POP
```

The real file is `Kernel/Wizardry/LanguageSelect/LanguageSelect_Installer.event`.

Regenerating `.lyn.event` files can change other features' output. `4367e1604` also changed five unrelated `.lyn.event` files (`Lvupfx/Lvupfx/MapLvup`, `ModularMinimugBox`, `OverflowDetection`, `TextEngineRework`, `VeslyUI/C_Code`). The cause was not checked. After `make`, read `git status` and keep only what your change caused.

## Checklist

Replace `Example` with your feature name. Each step lists the file and the line to add. The paths in backticks use `<Feature>` for the folder.

1. Create `Kernel/Wizardry/<Feature>/` with `<Feature>_Installer.event` (template in [Installer and lyn](#installer-and-lyn)) and `Source/<Feature>.c`.

2. Start the `.c` with the include set in [Header and includes](#header-and-includes).

3. Include the installer from `Kernel/Wizardry/wizardry.event`. Add this line inside the `#ifdef WIZARDRY_CUSTOM` block (`wizardry.event:129-191`), near the other installers in alphabetical order (the block is mostly, not strictly, alphabetical):

   ```
   #include "Example/Example_Installer.event"
   ```

   Use the `WIZARDRY_TEXT` block (`wizardry.event:41-127`) only for code that must sit in kernel `.text`. See [Where the code goes](#where-the-code-goes-kernel-vs-wizardry_custom).

4. Generate the `.lyn.event` and commit it. Run `make` (needs `DEVKITPRO` and `DEVKITARM` set, see `Documentation/Setup.md`). The rule that writes `Source/<Feature>.lyn.event` from the `.c` is `makefile:187`. Commit the generated file together with the `.c`.

5. Only if a vanilla function is rewritten: put `LYN_REPLACE_CHECK(<Func>);` before the function in the `.c` (macro at `include/common-chax.h:26`), and create `Source/LynJump.event`. Format in [Installer and lyn](#installer-and-lyn). The installer includes it first:

   ```
   #include "Source/LynJump.event"
   ```

6. Optional, runtime on/off: three edits, see [Runtime toggle](#runtime-toggle-designer-config).

7. Optional, compile-time switch: one line in `include/configs/configs.h`, see [Compile-time switch](#compile-time-switch).

8. Optional, RAM: one line in `include/link/config-memmap.s`:

   ```
   _kernel_malloc sExampleState, 0x10
   ```

   `_kernel_malloc` takes from the top-down pool (`FreeRamSpace`), and `_kernel_malloc2` from the bottom-up pool (`FreeRamSpace2`), as LanguageSelect did (`include/link/config-memmap.s:18-38`). `_kernel_malloc_demo` is the demo pool; no file in the tree uses it. Check usage with `make ramcheck` (`makefile:498`). Its output was not run for this doc.

9. Optional, designer text: a `.txt` under `Contents/Texts/Source/texts/` and an include in `Contents/Texts/Source/kernel.txt`. See [Text](#text).

10. Optional, header: `include/kernel/<feature>.h`. See [Header and includes](#header-and-includes).

11. Optional, data tables: designer-facing tables go in `Data/`, and kernel code reaches them through a `gp` pointer line. See [Where the code goes](#where-the-code-goes-kernel-vs-wizardry_custom).

12. Documentation: `Documentation/Features/<Feature>.md`, a README bullet, and an optional GIF. See [Documentation](#documentation).

13. Build and check. Run `make`. Watch for an `Assertion error` from the `ASSERT` at `Kernel/kernel.event:41` (kernel `.text` is full, see the root `CLAUDE.md` pitfalls). Run `./check_codingstyle.sh <file.c>` on each new `.c`. Check `git status` for unrelated `.lyn.event` changes. Do not commit unless asked.

## Where the code goes: kernel vs WIZARDRY_CUSTOM

### The three blocks in wizardry.event

`Kernel/Wizardry/wizardry.event` has three blocks. `Kernel/kernel.event` and `main.event` place each block in a different ROM area.

| Block in `wizardry.event` | Pulled in by | Area | Use it for |
|---|---|---|---|
| `#ifdef WIZARDRY_DATA` (lines 1-39) | `Kernel/kernel.event:21-28` (`ORG KernelSpace_KData`) | kernel data | hook lists (`data.event` files) |
| `#ifdef WIZARDRY_TEXT` (lines 41-127) | `Kernel/kernel.event:30-41` (`ORG KernelSpace_Text`) | kernel `.text`, in BL range, `0x7C000` bytes at `0xE8414` (`include/configs/config-memmap.h:15-16`) | code that must be in kernel `.text`. Nearly full |
| `#ifdef WIZARDRY_CUSTOM` (lines 129-191) | `main.event:57-62` (`ORG FreeSpaceDEMO`) | `FreeSpaceDEMO` at `0x1000000` (`include/configs/config-memmap.h:27`) | new features that are not hot. Plenty of room |

`WIZARDRY_CUSTOM` is defined at `main.event:60`, just before `#include "Kernel/Wizardry/wizardry.event"`, and undefined at `main.event:62`. `Kernel/kernel.event` defines `WIZARDRY_DATA` and `WIZARDRY_TEXT` the same way.

The rule: put a feature in the `WIZARDRY_CUSTOM` block unless it has to be in kernel `.text`. All three reference commits did this. `3f9a1e53a` says so in its message: "New code lives in FreeSpaceDEMO (WIZARDRY_CUSTOM) to keep kernel .text under its limit." Performance rules for hot paths still apply (see [Code rules](#code-rules)).

### Data/, Kernel/Data/ and Kernel/Wizardry/

| Folder | Pulled in by | What lives there | Example |
|---|---|---|---|
| `Data/` | `main.event:31-32` (`ORG FreeSpace_UsrData`, `#include "Data/Data.event"`). This is in the none-secure part of `main.event`, after its "None-secure data" banner | designer-facing tables and config: `DesignerConfig/`, `SkillSys/`, `ClassData/`, `CombatArt/Data/` | `Data/DesignerConfig/designer-config.c` |
| `Kernel/Data/` | `Kernel/kernel.event` (`#include "Data/data.event"`, inside `ORG KernelSpace_KData`) | kernel-owned tables: the SkillSys menu tables and ItemSys | `Kernel/Data/SkillSys/Data/SkillMenuInfo.c` |
| `Kernel/Wizardry/` | `wizardry.event` in its three blocks | feature code, generated `.lyn.event`, and feature `data.event` hook lists | `Kernel/Wizardry/PostActionHook/data.event` |

A rule of thumb from this layout (not written down elsewhere): table values that a designer edits go in `Data/`. Code and hook lists go in `Kernel/Wizardry/`. Tables that only the kernel reads go in `Kernel/Data/`.

### How kernel code reaches a Data table

Kernel C code reads `Data/` tables through a `gp` pointer. The pointer is a reloc word, `gpName: POIN tableName`, in one of two files:

- `Preload/Reloc.event`, included by `main.event:27`. Its `gp` words point at tables under `Data/`. All 100 pointer lines name a symbol that also appears under `Data/` (a grep check; the definitions were not all opened). Examples: `gpKernelDesignerConfig: POIN gKernelDesigerConfig` (`Preload/Reloc.event:45`), `gpKernelBattleDesignerConfig` (`:134`), `gpSkillInfos` (`:8`).
- `Kernel/Preload/KernelReloc.event`, included by `Kernel/kernel.event:16`. Its `gp` words point at kernel lists and tables under `Kernel/Wizardry/` (47 of its 49 lines, by the same grep check; the other two are not under `Kernel/Wizardry/`). Examples: `gpPostActionFuncs: POIN gPostActionFuncs` (`Kernel/Preload/KernelReloc.event:15`), `gpKernelArmFunConfig` (`:45`).

Rule: a table under `Data/` gets its `gp` line in `Preload/Reloc.event`. A table under `Kernel/Wizardry/` or `Kernel/Data/` gets it in `Kernel/Preload/KernelReloc.event`.

The C side declares the pointer in a header and reads through it:

- `extern const struct KernelDesigerConfig *const gpKernelDesignerConfig;` (`include/kernel/kernel-lib.h:232`)
- `extern HookProcFunc_t const *const gpPostActionFuncs;` (`include/kernel/post-action.h:5`)

For the designer config, the `Data/` symbol appears in C only at its definition (grep). Kernel code uses the pointer.

`Kernel/fake-nonsec-reloc.event` is a generated copy of `Preload/Reloc.event` (`makefile:511-519`). `Kernel/kernel.event:13` includes it before the other Preload files. Do not edit it.

## Installer and lyn

### Installer template

```
#ifndef EXAMPLE_INSTALLED
#define EXAMPLE_INSTALLED

/**
 * One or two lines: what this installs and where it lives
 * (WIZARDRY_CUSTOM, so FreeSpaceDEMO).
 */
#include "Source/LynJump.event"
#include "Source/Example.lyn.event"

#endif /* EXAMPLE_INSTALLED */
```

The guard is the form `PopupIconShine_Installer.event` and `ClassGrowths_Installer.event` use. Of the 56 `*_Installer.event` files tracked under `Kernel/Wizardry/`, 12 have a guard. `LanguageSelect_Installer.event` has none. Add the guard. Leave out the `LynJump.event` line if there is no LynJump file.

### How the .lyn.event is generated

- A `.c` under `Kernel/` uses the rule for `Kernel/` files at `makefile:187-193`. It compiles with the kernel `CFLAGS` (`makefile:152`), runs `lyn` (`Tools/EventAssembler/Tools/lyn`), and appends `PROTECT` lines from `Tools/scripts/lynjump-protector.sh`.
- A `.c` anywhere else uses `%.lyn.event: %.c` (`makefile:211-217`). `Data/DesignerConfig/designer-config.lyn.event` is built this way.
- The `.lyn.event` files are committed. 847 of them are tracked (`git ls-files | grep -c '\.lyn\.event$'`). Regenerate with `make`, then commit the result. `CLAUDE.md` notes that some have hand edits, so check the diff first.

### LynJump.event format

From `Documentation/CONTRIBUTING.md`, with `PopupIconShine` as the live example (`Kernel/Wizardry/PopupIconShine/Source/LynJump.event`):

```
PUSH
ORG $11254
ALIGN 4
WORD $46C04778 $E59FC000 $E12FFF1C
POIN PopupIconUpdateProc_Loop
POP
```

- `ORG $XXXXX` is the ROM offset: the address minus `0x08000000`. `ORG $11254` is address `0x08011254`.
- The three `WORD`s are a trampoline. Decoded by hand: Thumb `bx pc` and `nop`, then ARM `ldr r12, [pc]` and `bx r12`, which jumps to the `POIN` target. The repo does not document this.
- `POIN` names your replacement function. Define it in the `.c` under that name, with `LYN_REPLACE_CHECK(name);` before it.
- One block per replaced address. `ClassGrowths/Source/LynJump.event` has three.
- `LYN_REPLACE_CHECK(name)` expands to a `static` pointer that takes the function's address (`include/common-chax.h:26`). Its stated purpose is to catch breakage from future C-Lib changes (`Documentation/CONTRIBUTING.md`, Mandatory Requirements).

### Finding a vanilla function's address

1. Name to address. The file is `Tools/FE-CLib-Mokha/reference/fireemblem8.sym`, one `ADDR NAME` pair per line. This is the file the makefile reads as `FE8_SYM` (`makefile:17`):

```
grep " ClassChgMenuExec$" Tools/FE-CLib-Mokha/reference/fireemblem8.sym
080CDD78 ClassChgMenuExec
```

   The ORG is the address without its leading `08`: `0CDD78`, so `ORG $cdd78` (`ClassGrowths/Source/LynJump.event`).

2. Address to name: `grep -i "^08011254 " Tools/FE-CLib-Mokha/reference/fireemblem8.sym`.

3. Unnamed functions are called `sub_<ADDR>`. For example `sub_80CCF60` at `080CCF60` (ClassGrowths replaces it).

4. The root `fe8-kernel-dev.sym` is the symbol map of the last built ROM. It is gitignored (`.gitignore`, `*.sym`) and written by the EventAssembler step at `makefile:140`. It also lists vanilla addresses, but use the reference file, which is the one the build reads.

5. The protector script looks the replaced address up in the same reference file (`Tools/scripts/lynjump-protector.sh`), so the address should be a symbol in it.

## Runtime toggle (designer config)

The three reference commits each made the same three edits:

1. `include/kernel/kernel-lib.h`: add the field as the last line of `struct KernelDesigerConfig` (the struct starts at line 8 and closes at line 202). The name is snake_case. The spelling `KernelDesigerConfig` is the real one:

```
	u8 example_toggle; /* one line: what it does */
```

2. `Data/DesignerConfig/designer-config.c`: add the initializer to `gKernelDesigerConfig`, in alphabetical order. All 178 keys are in order now, so keep it that way:

```
	.example_toggle = true, // one line: what it does
```

3. `Documentation/Features/SystemConfig.md`: add a row to the designer config table (its header row is at line 11, `| Field | Description |`):

```
| `<name>` | What it does. See [<Feature>](./<Feature>.md). |
```

`make` then regenerates `Data/DesignerConfig/designer-config.lyn.event` (by the rule at `makefile:211`). `Data/Data.event:6` includes it. Commit the regenerated file; the three commits all did.

How code reads it: `gpKernelDesignerConfig->example_toggle`. The pointer is declared at `include/kernel/kernel-lib.h:232`. Examples: `Kernel/Wizardry/PopupIconShine/Source/PopupIconShine.c:185` (`if (gpKernelDesignerConfig->popup_item_icon_shine)`) and `Kernel/Wizardry/ClassGrowths/Source/ClassGrowths.c:14` (a `switch`). Check the toggle in the code, not in the installer. The installer is always included, and the toggle is read at run time. For a check used in many places, add a `static inline` helper, as `KernelLvupReplacesGrowths()` does (`include/kernel/kernel-lib.h:235`) and `ClassGrowthPreviewEnabled()` does (`include/kernel/lvup.h`).

### Does field order matter?

- In the C initializer: no. The initializer uses designated fields, so line order does not change the values. Keep it alphabetical anyway.
- In the struct: yes, it sets the byte layout of `gKernelDesigerConfig`. Append new fields at the end. Each of the three commits added its field as the new last line. A field inserted in the middle shifts every later offset. The C code is recompiled, so the code stays correct, but the FEBuilder layout below would be wrong.
- FEBuilder layout: `Patches/PATCH_DesignerConfig.txt` maps `B<n>` to a field name by position. It is hand-kept and stale. Its last field is `weapon_rank_skills` (`B169`, `DATASIZE=170`). Comparing by field index, 84 of its 156 entries match the struct, and 22 struct fields have no entry. Git history: `git log -- Patches/PATCH_DesignerConfig.txt` shows its last change was `82a1b0d9a`, and the three reference commits did not touch it. This doc does not fix it.
- A second, tracked copy, `Kernel/Wizardry/KernelLib/Source/designer-config.lyn.event`, is not included by any `.event` file in the tree (grep). The one that is built is `Data/Data.event:6`. Do not edit the copy.

## Compile-time switch

- Add the switch to `include/configs/configs.h`: `#define CONFIG_<NAME>` turns it on, and `// #define CONFIG_<NAME>` leaves it off. `configs.h:4` explains why some switches are build-time: "These need to remain as build time configs due to predominately using event/asm files". Use a compile-time switch only when a runtime toggle cannot work. Otherwise use the designer config.
- Gate with `#ifdef CONFIG_<NAME>`, not `#if`. `configs.h` says "Event Assembler only understands #ifdef, so do not use #if/#error here". Examples: `Kernel/Wizardry/wizardry.event:130` (`#ifdef CONFIG_FE8_REWRITE`), `Kernel/Wizardry/Arena/Arena.event:4` (`#ifdef CONFIG_ARENA_LIMITS`), `Kernel/Wizardry/BwlRework/source/BwlSupport.c:298` (C side).
- `include/common-chax.h:7` includes `configs/configs.h`, and `main.event:5` includes it too. So both C and `.event` files see the switches.
- Build flags live in `configs.mk` (for example `export CONFIG_LONG_CALL?=1` at `configs.mk:2`). Those are not feature switches.
- `include/configs/configs.h:59` says a full `make clean` may be needed when `CONFIG_FOURTH_ALLEGIANCE` is undefined. Whether that applies to other switches is unverified.

## Text

1. Create `Contents/Texts/Source/texts/<Name>.txt`. There are 40 files there. `Menu_Options.txt` and `StartMapEffects.txt` are small examples.

2. Format. Each message is a `## MSG_<NAME>` line, then the text on the following lines, and `[X]` ends it. From `Contents/Texts/Source/texts/Menu_Options.txt`:

```
## MSG_MENU_OPTION_ON
ON[X]

## MSG_MENU_OPTION_OFF
OFF[X]
```

   `[N]` is a newline and `[X]` is the end (`Contents/Texts/textdefs.txt`: `[X] = 0`, `[N] = 1`). Comments are stripped (`text_preprocess` in `Contents/Texts/Scripts/textprocess-chax.py`).

3. Include it from `Contents/Texts/Source/kernel.txt`. Add this line before the last line of the file, which is the `CustomCampaign/Text/Text.txt` include. `Menu_Options.txt` sits in that position now:

```
#include "texts/<Name>.txt"
```

4. Message IDs are assigned in include order (`current_index` in `textprocess-chax.py`). A file included in the middle shifts the IDs after it. Code uses the generated names, so that is safe for code. Whether anything stores a raw ID is unverified.

5. `make` runs the `text` pre-build target (`makefile:264-265`) and writes `Contents/Texts/build/msgs.h`. That file is gitignored (`Contents/Texts/.gitignore:2`). Do not edit it.

6. In C, add `#include "constants/texts.h"` and use `MSG_<NAME>` as a constant. `include/constants/texts.h` includes the generated `msgs.h`. Example: `Kernel/Wizardry/StartMapEffects/Source/StartMapEffects.c:71`. To read the string at run time: `GetStringFromIndex(MSG_<NAME>)` (`Tools/FE-CLib-Mokha/include/functions.h:65`; call site at `Kernel/Wizardry/Goals/GoalDisplay.c:82`).

## Header and includes

The top of the three reference `.c` files:

```c
#include "common-chax.h"
#include "kernel-lib.h"
/* feature headers, e.g. "lvup.h" (ClassGrowths.c), "language-select.h" (LanguageSelect.c) */
/* "constants/texts.h" only when the file uses MSG_ names (PopupIconShine.c, StartMapEffects.c) */
```

- PopupIconShine.c: `common-chax.h`, `kernel-lib.h`, `icon-rework.h`, `popup.h`, `popup-reowrk.h`, `constants/texts.h`.
- LanguageSelect.c: `common-chax.h`, `kernel-lib.h`, `gamecontrol.h`, `bmsave.h`, `language-select.h`.
- ClassGrowths.c: `common-chax.h`, `kernel-lib.h`, `lvup.h`, `strmag.h`.

`common-chax.h` goes first, then `kernel-lib.h`. It brings in `configs/configs.h`, which holds the compile-time switches.

Include paths come from `makefile:148` (`INC_DIRS := include include/kernel $(LIB_DIR)/include`):

- A header in `include/kernel/` is `"name.h"`.
- A header in `include/constants/` is `"constants/name.h"`.
- `include/jester_headers/` needs its folder name: `"jester_headers/custom-arrays.h"` (`StartMapEffects.c`).
- The FE-CLib headers (`popup.h`, `gamecontrol.h`, `bmsave.h`) are in `Tools/FE-CLib-Mokha/include/`.

Where a new header goes: `include/kernel/<feature>.h`. Use `#pragma once`, which 53 of the 57 headers there use. Start it with `#include "common-chax.h"` (see `include/kernel/language-select.h:1-3`). Declare the `extern` pointers and functions in the header, define them in the `.c`, and extend an existing header such as `include/kernel/lvup.h` when the feature belongs there.

## Documentation

1. `Documentation/Features/<Feature>.md`. Two recent examples:
   - `Documentation/Features/ClassGrowths.md`: title, index, introduction, modes, a code locations table (`| Feature | Location | Description |`), and limitations.
   - `Documentation/Features/LanguageSelect.md`: title, GIF block, behaviour, a config section naming the toggle, and a code locations list.

   Use this order: title; GIF block if there is one; what it does; a config section if there is a toggle; code locations with relative links such as `../../Kernel/Wizardry/...`; limitations.

2. Toggle row: `Documentation/Features/SystemConfig.md`, as in [Runtime toggle](#runtime-toggle-designer-config).

3. README bullet: `README.md` has a `## Features` list (line 14) in alphabetical order. Add a bullet. If you have a GIF, add a blank line and a tab-indented `<details>` block under it:

```
- [<Feature>](./Documentation/Features/<Feature>.md)

	<details>
		<summary>Preview</summary>
		<img src="./Documentation/Gifs/<Feature>.gif" alt="<Feature> preview" width="600" />
	</details>
```

   ClassGrowths has a bullet and no GIF (`README.md:77`), so the `<details>` block is optional.

4. GIF: `Documentation/Gifs/<Title_With_Underscores>.gif`, for example `Popup_Item_Icon_Shine.gif` or `Language_Select.gif`. The folder has 45 GIFs. A GIF is optional.

## Code rules

- Kernel `.c` files build with `-Werror` (`makefile:152`), so any warning fails the build.
- Linux kernel style. Check each file with `./check_codingstyle.sh <file.c>` ([`Documentation/CONTRIBUTING.md`](../CONTRIBUTING.md), Code Style).
- A vanilla replacement needs `LYN_REPLACE_CHECK` and a `LynJump.event`. See [`CLAUDE.md`](../../CLAUDE.md#rules).
- Kernel `.text` is nearly full. Put non-hot code in the `WIZARDRY_CUSTOM` block. See [`CLAUDE.md`](../../CLAUDE.md#pitfalls).
- Signed `%` is broken. Use `Div` or `DivRem`. See [`CLAUDE.md`](../../CLAUDE.md#pitfalls).
- Hot paths (battle calc, stat getters, `SkillTester`, map task, movement generation) need extra care. See [`Documentation/CONTRIBUTING.md`](../CONTRIBUTING.md), Suggestions.
- Generated files: `*.lyn.event`, `Contents/Texts/build/msgs.h`, `Kernel/fake-nonsec-reloc.event` and the root `*.sym`. Regenerate them with `make` and do not edit them by hand. Check the diff first.
- The SID guard `#if defined(SID_x) && (COMMON_SKILL_VALID(SID_x))` is for skills only. See [`../SkillTypes/Common.md`](../SkillTypes/Common.md).
- When you grep, use `--exclude-dir=.claude`. See [`CLAUDE.md`](../../CLAUDE.md).
- Do not commit, branch or push unless asked. See [`CLAUDE.md`](../../CLAUDE.md).
