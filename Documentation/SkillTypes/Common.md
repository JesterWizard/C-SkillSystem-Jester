# Common steps for every skill

> Applies to every skill type. Per-type files in this directory add their own hook and code steps on top of these. Paths are relative to the repo root. Line numbers were checked against the tree when this file was written.

## Skill ID ranges and which enum file

**Active list:** `include/constants/skills-equip.enum.txt` is the only enum file the build reads (`makefile:404`). One non-blank, non-comment line = one skill. Its ID is its position: the Nth active line gets `0x000 + N` (`Tools/scripts/enum2h.py:17-23`). Current state: 913 active lines, `SID_Dismount` = `0x001` (line 2) through `SID_VictorySmite` = `0x391` (line 983). `SID_Pivot` is line 35, so it is `0x022`.

**Other lists:**
- `include/constants/skills-class.enum.txt` (base `0x400`), `skills-person.enum.txt` (base `0x500`), `skills-item.enum.txt` (base `0x600`). Every line in these three files is a `// SID_x` comment. The makefile calls that would read them are commented out (`makefile:405-407`, `409`, `411`, `413-415`), so nothing from them reaches the build.
- A `// SID_x` line means "not active". `enum2h.py` and `enum2combo.py` skip any line starting with `/` (`Tools/scripts/enum2h.py:17-18`), so a comment neither gets an ID nor takes a slot. In the class/person/item files the comments are placeholders that mirror the equip list. The mirror is not exact: class line 68 is `// SID_Dance` where equip line 68 is `SID_DancePlus`.
- Uncommenting a class/person/item line has no effect unless its makefile call is also re-enabled. Those bases (`0x400+`) are not valid under `COMMON_SKILL_VALID` (`include/kernel/skill-system.h:90`, requires `< 0x400`). Enabling them as written would produce skills that are never valid. Unverified: whether that was intended.

**How the build generates headers** (`enum` target, `makefile:397-430`, in `PRE_BUILD` at line 430, so plain `make` runs it):
1. `Tools/scripts/enum2h.py 0x000 include/constants/skills-equip.enum.txt >> include/constants/skills.h` writes `#define SID_x 0x0NN` lines (`makefile:404`).
2. `Tools/scripts/enum2combo.py` writes `Patches/combo.skills*.txt` (`makefile:408`, `412`). These are generated.
3. `include/constants/skills.event` is the `#define SID_` lines of `skills.h`, copied for Event Assembler (`makefile:425-429`).
- `include/constants/skills.h` is gitignored (`include/constants/.gitignore:1`). `include/constants/skills.event` is tracked but regenerated by `make`. Never edit either. Edit the `.enum.txt` source.
- The whole block is skipped when `CONFIG_CI_NO_SKILL_TEST=1` (`makefile:403`). The default is 0 (`configs.mk:6`), so a normal `make` runs it.

**ID ranges, current config:**
- `CONFIG_TURN_ON_ALL_SKILLS` is defined at `include/configs/configs.h:74`. With it, `EQUIP_SKILL_VALID` is `0x001-0x3FF` (`include/kernel/skill-system.h:85`). Without it, `0x01-0xFE` (`skill-system.h:87`).
- `COMMON_SKILL_VALID` is `0x001-0x3FF` in every config (`skill-system.h:90`). Every skill `#if` guard uses it.
- `enum2h.py` stops at `0x3FF` (`Tools/scripts/enum2h.py:26-27`).
- Conflict with the docs: `Documentation/Features/SkillSys.md:8-12` and `:21` say `0x300-0x3FF` is item-only and that fixed item skills must be in that range. The enum does not enforce this. `SID_FlierGuidance` is `0x300` (`include/constants/skills-equip.enum.txt:793`), an equip-list entry. Treat `0x300+` as ordinary IDs.

**Adding a new SID:** IDs are positional. Inserting a line in the middle renumbers every later SID. Append the new name at the end of the active list (after `SID_VictorySmite`, currently `0x392`). A `////////` grouping header is allowed in the middle of the file because comments take no ID. Renumbering would change what existing saves and any hard-coded numeric SIDs refer to. Unverified: exactly how save data stores skill IDs.

## Checklist

Traced from `SID_Pivot` (menu skill) and `SID_Fury` (passive, `Skills_StatusGetter.txt`). Steps 1, 3-8 are needed by both. Step 2 is a mirror placeholder with no build effect. Step 9 is menu-only: Fury has no entry in `Kernel/Data/SkillSys/Data/SkillMenuInfo.c` or `SkillActionInfo.c` (grep finds none), and no frozen-help (FRtext) message. Steps 10-12 are optional.

Replace `Example` with your name and `SID_Example` with the SID.

1. `include/constants/skills-equip.enum.txt`: append `SID_Example` after the last active line (currently `SID_VictorySmite`, line 983). The new ID is its position. Check that the file has no duplicate name.
2. `include/constants/skills-class.enum.txt`, `include/constants/skills-person.enum.txt`, `include/constants/skills-item.enum.txt`: append `// SID_Example` at the end, as a placeholder. No build effect. The files are not aligned line-for-line.
3. `Contents/Texts/Source/texts/Skills_<Category>.txt`: append the NAME and DESC entries (see Text entries for the format and file list).
4. `include/kernel/Skills_Price.h`: add `#define MSG_SKILL_Example_PRICE 1000`.
5. `include/kernel/Skills_Capacity.h`: add `#define MSG_SKILL_Example_CAPACITY 1`.
6. `Data/SkillSys/Source/SkillInfo.c`: add the guarded `[SID_Example] = { ... }` block (template in SkillInfo entry).
7. Icon (optional): `Contents/Gfx/Sources/SkillIcon/<Name>.png`, then use `.icon = GFX_SkillIcon_Example` in step 6. Without a PNG, use `.icon = GFX_SkillIcon_WIP`.
8. Effect code: put the code in a `.c` file with the guard `#if defined(SID_Example) && (COMMON_SKILL_VALID(SID_Example))`. Its generated `.lyn.event` must be `#include`d from an installer. For most skill effects that is `Kernel/Wizardry/SkillEffects/MiscSkillEffects.event` (e.g. line 67 for Pivot: `#include "MenuSkills/Pivot.lyn.event"`). The `.lyn.event` is produced by the `%.lyn.event` rule (`makefile:211`).
9. Menu-only: `Kernel/Data/SkillSys/Data/SkillMenuInfo.c` (add a `[SID_Example] = &(const struct MenuItemDef) {...}` block, Pivot at lines 577-590) and `Kernel/Data/SkillSys/Data/SkillActionInfo.c` (`[SID_Example] = Action_Example,`, Pivot at lines 138-139). Also `MSG_SKILL_Example_FRtext` if the menu uses frozen help (`Kernel/Wizardry/SkillEffects/MenuSkills/Pivot.c:60`).
10. Prototypes: add to `include/kernel/skill-system.h` for any function used from another file (Pivot: lines 557, 558, 710).
11. Optional synthesis recipe: in `Kernel/Wizardry/SkillSys/PrepSkill/SkillSynthRecipes.event`, add `SkillSynthRecipe(SID_A, SID_B, SID_Example)` above the terminator `SkillSynthRecipe(0, 0, 0)` (line 135).
12. Optional fixed assignment or skill tree: see Giving the skill to a unit.
13. Run `make`. The `enum`, `text` and `gfx` pre-build targets regenerate `include/constants/skills.h`, `Contents/Texts/build/msgs.h` and `Contents/Gfx/GfxDefs.h` (`makefile:430`, `265`, `345`).
14. Type-specific hooks (hook lists, engine callbacks): see the per-type file.

## Text entries

**Format.** A `## MSG_SKILL_<Name>_NAME` line, then the text. The text block ends at the next line that starts with `#`, so text lines must not start with `#` (`Contents/Texts/Scripts/textprocess-chax.py:163-203`). Lines are joined with no separator, so every source line needs `[N]` (newline) or `[X]` (end) at its end. The codes are defined in `Contents/Texts/textdefs.txt:1` (`[X] = 0`) and `:3` (`[N] = 1`). Example, `Contents/Texts/Source/texts/Skills_Menu.txt:301-305`:

```
## MSG_SKILL_Pivot_NAME
Pivot[X]
## MSG_SKILL_Pivot_DESC
Pivot:[N]
Allows unit to move to the[N]
opposite side of an adjacent ally.[X]
```

**Include chain.** `Contents/Texts/texts.txt` includes `Source/kernel.txt`, which `#include`s each `texts/Skills_*.txt` (`Contents/Texts/Source/kernel.txt:13-33`). The 21 files below are already included. A new skill needs no new file.

**Generation.** `make text` (`makefile:262-269`) runs `Contents/Texts/makefile`, which runs `Contents/Texts/Scripts/textprocess-chax.py` on `texts.txt`. It writes `Contents/Texts/build/msgs.h` (`#define MSG_SKILL_Pivot_NAME 0x13AF`, line 5045). `include/constants/texts.h` includes that header, and C code uses the name.

**ID assignment.** `textprocess-chax.py` uses one running counter, `current_index`, across all included files (`:141`, `:182`, `:203`). Each `## MSG_...` takes the next number. A `#0x...` line would set it explicitly (`RE_MSGIDX`, `:11`, `:165`), and no `Skills_*.txt` file uses one. Adding an entry in the middle therefore shifts every later MSG number. C code uses names, so this is safe, but do not hard-code numeric MSG IDs.

## SkillInfo entry

Struct, `include/kernel/skill-system.h:125-129`:

```c
struct SkillInfo {
	const u8* icon;
	u16 name, desc, price, capacity;
	u8 iconPal;
};
```

The table is `const struct SkillInfo gSkillInfos[MAX_SKILL_NUM + 1]` in `Data/SkillSys/Source/SkillInfo.c:9`. Entries are designated initializers, so their position in the file does not matter.

Template, adapted from `SID_Pivot` (`Data/SkillSys/Source/SkillInfo.c:6289-6298`):

```c
#if (defined(SID_Example) && COMMON_SKILL_VALID(SID_Example))
    [SID_Example] = {
        .name = MSG_SKILL_Example_NAME,
        .desc = MSG_SKILL_Example_DESC,
        .capacity = MSG_SKILL_Example_CAPACITY,
        .price = MSG_SKILL_Example_PRICE,
        .icon = GFX_SkillIcon_WIP,
        .iconPal = 0,
    },
#endif
```

`iconPal = 0` selects palette bank 0, the default. See the Icon section.

Readers: the accessors are in `Kernel/Wizardry/SkillSys/kernel/Infos.c` and declared at `include/kernel/skill-system.h:133-151`.

## Price and capacity

- `include/kernel/Skills_Price.h:568`: `#define MSG_SKILL_Pivot_PRICE 1000`.
- `include/kernel/Skills_Capacity.h:568`: `#define MSG_SKILL_Pivot_CAPACITY 1`.
- Price is read by `GetSkillPrice` (`Kernel/Wizardry/SkillSys/kernel/Infos.c:55-57`). No caller exists in the repo (grep), so price has no effect today.
- Capacity is read by `GetSkillCapacity` (`Infos.c:60-62`). It is used only by the capacity system, gated on `gpKernelDesignerConfig->tellius_skill_capacity_system`: in `GetUnitBattleAmt` (`Kernel/Wizardry/StatScreen/DrawUnitPage/Source/Util.c:13`) and in the skill-learning check (`Kernel/Wizardry/SkillSys/SkillScroll/Source/SkillScroll.c:235-238`). With the flag off, capacity has no effect.

## Icon

- Source PNG: `Contents/Gfx/Sources/SkillIcon/<Name>.png` (e.g. `Fury.png`). Name it after the SID name.
- `make` runs `Contents/Gfx/makefile`, which runs `Contents/Gfx/Scripts/gfx-installer.sh` when any PNG changes. For each PNG the script emits:
  - `GFX_SkillIcon_<Name>:` with an `#incbin` of `<Name>.4bpp` into `Contents/Gfx/GfxInstaller.event` (`gfx-installer.sh:21-23`).
  - `extern const unsigned char GFX_SkillIcon_<Name>[];` into `Contents/Gfx/GfxDefs.h` (`gfx-installer.sh:24`).
  - The name is the path after `Sources/` with `/` turned into `_` and `.png` removed. The top-level `gfx` target is at `makefile:344-352`.
- The PNG is converted to 4bpp by the pattern rule `%.4bpp: %.png` (`makefile:279-282`), using `GRIT4BPPARGS` (`makefile:106`).
- Unverified: how the `.4bpp` gets built before the EA link. `makefile:137` passes `ea-dep --add-missings` into the link prerequisites, which probably pulls in the `.4bpp` rule. Check that `Contents/Gfx/Sources/SkillIcon/<Name>.4bpp` exists after `make`.
- No PNG: use `GFX_SkillIcon_WIP` (the placeholder). `SID_Pivot` has no PNG and uses it (`Data/SkillSys/Source/SkillInfo.c:6295`).
- Palette: `iconPal` picks bank 0 (default) or bank 1. The RGB values come from the icon art, not from `SkillInfo`. Details in `Documentation/Features/SkillIconPalettes.md`.

## Battle animation (optional)

`Data/SkillSys/Source/SkillAnimInfo.c` has two per-SID tables. Both use the same guard.

- `const u8 EfxSkillAnimPriority[MAX_SKILL_NUM + 1]` (`SkillAnimInfo.c:6`): `[SID_X] = EFX_PRIORITY_NORMAL,`. Values: `EFX_PRIORITY_LOW = 0x1`, `EFX_PRIORITY_NORMAL`, `EFX_PRIORITY_HIGH`, `EFX_PRIORITY_HIGHHIGH` (`include/kernel/skill-system.h:255-260`).
- `struct EfxAnimConf const *const EfxSkillAnims[MAX_SKILL_NUM + 1]` (`SkillAnimInfo.c:352`): `[SID_X] = &EfxSkillVanilla,`. `EfxSkillVanilla` is declared at `include/kernel/efx-anim.h:20`.

Template:

```c
#if (defined(SID_Example) && COMMON_SKILL_VALID(SID_Example))
	[SID_Example] = EFX_PRIORITY_NORMAL,
#endif
```

```c
#if (defined(SID_Example) && COMMON_SKILL_VALID(SID_Example))
	[SID_Example] = &EfxSkillVanilla,
#endif
```

- Missing entry: `NewEfxSkill` falls back to `gpEfxSkillVanilla` when the entry is not a ROM pointer (`Kernel/Wizardry/SkillSys/EfxSkill/EfxSkill.c:89-95`). `GetEfxSkillConf` does the same (`Kernel/Wizardry/SkillSys/kernel/Infos.c:149-157`).

**Registering a battle-hit animation.** Declared in `include/kernel/efx-skill.h`:

```c
void RegisterActorEfxSkill(int round, const u16 sid);   // include/kernel/efx-skill.h:23
void RegisterTargetEfxSkill(int round, const u16 sid);  // include/kernel/efx-skill.h:24
```

Implemented in `Kernel/Wizardry/SkillSys/EfxSkill/Utils.c:22` (actor) and `:33` (target). Each call stores the SID for one hit round. A call is dropped if the stored SID has a higher priority (`Utils.c:26-27`). At equal priority the later call wins. Callers use the hit round from `GetBattleHitRound`, e.g. `Kernel/Wizardry/BattleSys/Source/BattleHitAttr.c:20` (`SID_Eclipse`) and `:32` (`SID_Counter`, target side).

The animation data itself, `*.efx.txt` → `*.efx.event`, is a separate build step (`makefile:319-329`, rule `%.efx.event`). It is not needed for `EfxSkillVanilla`.

## Giving the skill to a unit

**Fixed assignment.** Tables in `Data/SkillSys/Source/`. Each table is keyed by a character, class, item or weapon ID. Most rows hold two SIDs (`[0]`, `[1]`):

| File | Table | Keyed by |
|---|---|---|
| `Data/SkillSys/Source/SkillTable-person.c` | `gConstSkillTable_Person[0x100][2]` | character, e.g. `[CHARACTER_EIRIKA]` |
| `Data/SkillSys/Source/SkillTable-job.c` | `gConstSkillTable_Job[0x100][2]` | class, e.g. `[CLASS_PALADIN] = { [0] = SID_Canto, }` |
| `Data/SkillSys/Source/SkillTable-item.c` | `gConstSkillTable_Item[0x100][2]` | item; skill held while the item is in the unit's inventory |
| `Data/SkillSys/Source/SkillTable-weapon.c` | `gConstSkillTable_Weapon[0x100][2]` | weapon; skill held while it is equipped |
| `Data/SkillSys/Source/SkillTable-forge.c` | `gConstSkillTable_Forge[0x100]` | forged weapon; one SID |
| `Data/SkillSys/Source/SkillTable-generic.c` | `gSkillPreloadPData[0x100]` | per-character preload; see the comment at the top of the file |
| `Data/SkillSys/Source/SkillTable-wrank.c` | `gSkillWRankTable` | weapon-rank prowess chain |

Readers: `GenerateSkillListExt` (`Kernel/Wizardry/SkillSys/kernel/SkillList.c:304`) reads person (`:353`), job, item (`:361`), weapon and shield (`:372`), and the forged-weapon skill. The `gpConstSkillTable_*` pointers are declared at `include/kernel/skill-system.h:119-123`.

Gotcha: the existing rows in `SkillTable-job.c` and the other fixed tables have no `#if` guard (0 `#if` in the person, job, item and weapon files, 19 SID references in the job file). Wrap new rows in the guard anyway (see Code rules). Otherwise the build breaks if the SID is commented out.

**Synthesis.** `Kernel/Wizardry/SkillSys/PrepSkill/SkillSynthRecipes.event`: `SkillSynthRecipe(a, b, result)` lines, unordered pairs (`:3-4`). Terminator `SkillSynthRecipe(0, 0, 0)` at line 135. The consumer is `Kernel/Wizardry/SkillSys/PrepSkill/Source/CustomMenuOptions/SkillSynth.c`.

**Skill tree (optional).** `Data/SkillTree/Source/SkillTree.c`: `gSkillTreeSpCostTable` (line 12) holds the SP cost per SID and ends with `{ 0, 0 }`. `gUnitSkillTreeTable` (line 32) holds the per-unit tree. The only tree is a proof of concept for Eirika (`Documentation/Features/SkillTree.md:18`).

## Code rules

- **SID guard.** Wrap all skill-specific code in `#if defined(SID_Example) && (COMMON_SKILL_VALID(SID_Example))` ... `#endif`. The build must still compile with the SID commented out (`../CONTRIBUTING.md`, Mandatory Requirements). Examples: `Kernel/Wizardry/SkillEffects/MenuSkills/Pivot.c:15` and `Data/SkillSys/Source/SkillInfo.c:6289`.
- **Rewriting a vanilla function.** Put `LYN_REPLACE_CHECK(Func);` before the function (macro at `include/common-chax.h:26`). Add a `LynJump.event` in the same directory with the matching lynjump data. Example: `Data/SkillTree/Source/LynJump.event` (`PUSH`, `ORG`, `ALIGN 4`, `WORD`, `POIN`, `POP`).
